# 方法论

本文说明模型雷达图如何从公开证据得到页面上的分数。所有规则都写在 `radar/` 构建包、`radar/emit.py` 与 `data/` 的表中，本文是便于阅读的说明，不替代代码。

## 1. 总览

```text
data/raw_*.csv  ──┐
data/mapping.csv ─┼──> radar/families.py ──> data/scores.csv ──┐
data/canon.csv   ─┘                                          │
                                                             ├──> radar/emit.py ──> model-radar.html
data/dimensions.csv ─────────────────────────────────────────┤
data/weights.csv ────────────────────────────────────────────┤
data/models.csv ─────────────────────────────────────────────┘
```

整条链只有两步：

1. **证据 → 账本**：把各来源的原始分归一化，归入基准族，换算成族内位次分，写入 `data/scores.csv`。
2. **账本 → 页面**：过滤出计分证据，按维度求均值，按场景权重合成，写入 `model-radar.html` 的数据区。

页面不重算分数，只切换“看哪一档证据”。因此同一个模型在不同口径下的分数可能不同，但同一档口径下，页面与账本一致。

## 2. 八个能力维度

| 维度 | 一句话 | 典型证据 |
|---|---|---|
| 推理与知识 | 复杂推理、数理逻辑、通用与世界知识 | GPQA、HLE、CritPt、LiveBench Reasoning、SuperCLUE 数学/科学推理 |
| 代码 | 代码生成、修复、真实工程任务 | SciCode、LiveBench Coding、SWE-bench 系、SuperCLUE 智能体编程 |
| 指令遵循 | 严格按格式、字数、角色、约束输出 | IFBench、LiveBench IF、SuperCLUE 精确指令、AI产品狙击手 Q1 |
| Agent 与工具调用 | 函数调用、多步规划、工具使用 | Terminal-Bench、AutomationBench、τ²-bench、LiveBench Agentic / Browser |
| 长文本 | 长上下文理解、检索、多跳定位 | AA-LCR、SuperCLUE 长上下文 |
| 可靠性与低幻觉 | 事实准确、宁说不知道不编造 | AA Omniscience Index |
| 内容创作 | 中文文风、创意、结构化写作 | LiveBench Language、LiveBench 2.0 Research、AIWB、SuperCLUE-Writing |
| 图片与制图 | 图片理解、细节捕获、前端/页面设计复刻 | MMMU-Pro、Design Arena、LiveBench 2.0 Design |

维度定义、白话解释、典型任务与适用建议在 `data/dimensions.csv` 中维护；页面抽屉直接读取这张表。

## 3. 第一步：把原始分折算成 0–100 面值

不同来源的量纲不同。进入基准族之前，先做一次单调折算：

| 原始量纲 | 面值折算 |
|---|---|
| 0–100 / 百分制 | 原值 |
| 0–1 | ×100 |
| 0–1（越低越好） | 当前**未实现反转、也无映射**：代码的 `normalize()` 没有这一分支，误映射会直接报错；幻觉率类指标暂不入账。若未来接入，需先补 `(1 − x) × 100` 实现 |
| 10 分制 | ×10 |
| 5 分制 | ×20 |
| Elo / 自有指数 | 当期模型池内 min–max 线性映射到 60–100 |

这一步只是把不同报法拉齐到同一量纲。对同一基准族而言，Elo / 指数的 min–max 是单调变换，不会改变族内名次；真正决定位次分的还是原始分的大小关系。

## 4. 第二步：基准族与族内位次分

### 4.1 为什么需要“基准族”

同一个基准可能以不同名字、不同设置或不同来源出现；同一模型也可能被多个来源重复报告。例如：

- AA 的 HLE 与厂商模型卡的 HLE w/o tools → 同族 `HLE`；
- 同一模型在 AA 与厂商官方页各报一次的 Terminal-Bench 4.0 → 同族 `TB4.0`；
- 但版本/题目集不同则不并族：LiveBench 1.x 与 2.0、TB4.0 与 TB2.1。

如果不归族，同一模型可能因为“同一能力被多个来源重复报告”而获得额外权重。归族后，规则是：

> **同一（模型 × 基准族）只留一票。**

去重顺序：

1. 第三方来源优先于厂商自报渠道；
2. 同一渠道内，数据日期新者优先；
3. 被淘汰的行不进入 `scores.csv`，但仍保留在 `raw_*.csv` 中可溯源。

Terminal-Bench 是特例：在 `mapping.csv` 里 **TB4.0 与 TB2.1 是两个族**（两版难度差很大，不合并排名）；同时额外规定 **AA 的**同一模型只取一版——优先 TB4.0，缺则回退 TB2.1。被丢弃的 AA TB2.1 仍留档 raw，但不进账本；厂商渠道的 TB2.1 行保留在账本，但当前 `TB2.1` 族 n=3、样本不足，因此不计分。这是为了不让同一模型在 Agent 维吃两次 TB 权重。TB4.0 对很多模型分数很低，这是已知取舍，模型备注会写明。

### 4.2 位次分公式

对每个基准族：

1. 把族内所有模型的原始分**从低到高**排序；
2. 最低分记第 1 名；
3. 并列时取平均名次；
4. 位次分 = `(名次 - 0.5) / n × 100`。

其中 `n` 是该族内**去重后的模型数**。

含义：**在这个基准的模型池里，它赢过多少比例的对手。**

- n=4 时，四个名次对应 12.5 / 37.5 / 62.5 / 87.5；
- n=10 时，最高约 95，最低约 5；
- n=20 时，最高约 97.5，最低约 2.5。

分数越高，表示相对位置越靠前，不表示“准确率 90%”。一个 90 分的模型，不是“答对 90% 的题”，而是“在这个池子里约赢过 90% 的对手”。

### 4.3 小族怎么处理：v0.26 从「排除」改为「降权」

`FAMILY_MIN_N = 2`（入分门槛：族内至少 2 个模型才有排名）；降权档位 `FAM_WEIGHT`：**n≥4 ×1.0、n=3 ×0.6、n=2 ×0.35**。

n=2 时位次分只有 25 / 75 两档，n=3 时只有 16.7 / 50 / 83.3 三档，分辨率天然粗，容易被误读成“能力差距”——所以小族不是不许进，而是**按可信度降权参与**：证据仍然真实，只是话语权小。

- 族内 ≥2 人：计位次分，写入 `scores.csv`，`族内n` 保留真实人数，维度均值里按上表权重加权；
- 族内 =1 人：**不计分**。单模型无对手，位次分恒为 50、零信息量，计入只会制造“50=平庸”的误读。证据行保留、`榜单分` 留第一步面值，页面标注；
- 该族后来凑到更多模型时，下一次构建会自动提高它的权重。

完全排除（旧规则）会更“纯”，但会把真实测过的证据整块扔掉；不设权重灌进去会让小族噪声污染大榜。降权是两者之间的折中：**有数据就用，话语权按可信度分配**。

### 4.4 单基准标记 †

如果某模型某维只有 1 个计分族支撑，页面在该维加 **†**，并在图例、tooltip、抽屉里写明族名。

含义：**这一维只有单一来源，不等于模型弱，也不等于结论稳。** 点开证据抽屉，看清楚是哪个基准、池内多少人，再决定信多少。

## 5. 第三步：维度分与场景综合分

### 5.1 维度分

某模型某维的维度分 = 该维**所有计分族**位次分的**加权均值**（v0.26 起）。

- 只使用 `族内n ≥ 2` 的计分行；
- 权重按族内人数分级：n≥4 ×1.0、n=3 ×0.6、n=2 ×0.35；
- 同一族只算一票（去重后）；
- 不对不同基准做二次加权。

高置信族（n≥4）占绝对主导，小族只在它们缺席时才有可见影响。它不代表统计最优，但可解释、可复核，且不浪费任何真实证据。

### 5.2 场景综合分

五套场景各自给 8 个维度一组相对权重（`data/weights.csv`）。构建时按场景把权重归一化到 100.0，页面显示的是归一后的百分比。

综合分 = 该场景下**有计分证据的维度**的加权平均；缺失维度的权重自动让位，剩余维度重新归一化。

这意味着：

- 缺数据不会把综合分拉低到 0；
- 但覆盖越少，综合分的可比性越弱；
- 页面会在榜行显示 `n/8` 覆盖度，权重覆盖低于 60% 时标“低覆盖”，提示排名仅供参考。

### 5.3 为什么不做“未加权平均”

不同任务对能力的需求不同。把 8 维直接平均，会隐含“所有能力同等重要”的假设，和实际选型不符。场景权重是显式的取舍，用户可以看到、也可以不同意。

## 6. 三档数据口径

页面顶部有三个口径开关。它们只决定“哪些证据参与维度分”，不改写任何一条证据的位次分。

### 6.1 全部来源

使用 `scores.csv` 中所有计分证据，包括厂商自报渠道。

厂商自报渠道在 `radar/config.py` 的 `VENDOR_SRC` 中单点维护，目前包括：

- `Z.ai官方`
- `dots官方`
- `腾讯官方`
- `NVIDIA官方`
- `DeepSeek官方`
- `酥悠沫-官方`（酥悠沫转录的厂商自报表）

### 6.2 仅第三方榜单

整体排除上述厂商自报渠道，再按剩余计分证据重算维度分。

注意：这是**按渠道排除**，不是“按是不是自家模型排除”。因此 NVIDIA 官方页给其他厂商模型报的分也会被排除。

如果某模型某维只被厂商自报覆盖，该维在“仅第三方”下落“待定”，权重让位，**不是当 0 分**。

### 6.3 含推理补全

在“全部来源”的基础上，把 `data/raw_inferred.csv` 的推理值填进缺失格子。

- 推理值默认**不进入**维度分；
- 只有切到这一档才显示；
- 页面上用虚线 / 斜体 / “推理值”标注；
- 推理值不会覆盖任何实测证据，只填“该格一条计分证据都没有”的位置。

推理补全的两种方法：

1. **M1 同族前版直推**：同一模型家族的前一代与新一代在同一组官方基准上的差值，按位次口径外推。当前 **0 条**（DeepSeek-V4.1-Flash-1017 已补到 8/8 实测，不再需要 M1）；代码保留给未来同系列新版本。
2. **M2 池内 k 近邻**：在本池已计分的实测矩阵上，用**已有维度剖面**的 Pearson 相似度（共同维 ≥3）找最接近的 k=5 个模型，取相似度加权均值。当前 13 条推理值全部来自 M2。

两种方法都在已知格上做过留一验证（LOO），误差写进 `raw_inferred.csv` 的 `留一MAE` 列，并在页面抽屉同屏展示。它们仍然只是估计值，不是实测。

## 7. 数据新鲜度与版本

- `data/raw_*.csv` 的每一行都有 `数据日期` 与 `URL`；
- 页面数据区有构建日期；
- 本项目不是实时榜单，更新靠人工采集与 PR；
- 新版本模型原则上**单列一册**，不覆盖旧版本，便于比较升级是否真的发生；
- 只有精确同款版本才入账；版本对不上时宁可不收，不做跨版本外推（推理补全除外，且默认不计分）。

## 8. 已知限制

请在引用分数前读完这一节。

### 8.1 池内相对，不是绝对能力

位次分依赖当期模型池。增加或删除模型，会让全池分数整体移动。两个不同日期的截图不能直接逐格比较；跨期比较应看相对名次与证据覆盖，而不是绝对分数。

### 8.2 基准族归并是判断，不是真理

哪些基准算同一族、哪些不算，需要判断。例如 LiveBench 1.x 与 2.0 分开、AA 的 HLE 与厂商 HLE 合并、TB4.0 与 TB2.1 分成两个族（同时对同一模型只取一版，优先 4.0）。归并规则写在 `data/mapping.csv`，可以逐行讨论与修正。

### 8.3 构念效度

“代码”维把 SciCode、LiveBench Coding、SWE-bench 系等放在一起；它们测的不是同一种代码能力。维度分是这些基准族的等权平均，不能替代真实工程实测。

### 8.4 覆盖不均

有的模型 8/8，有的只有 2/8。覆盖少的模型，综合分更容易被少数维度主导。页面用 `n/8`、`†`、低覆盖提示来暴露这一点，但不能完全消除。

### 8.5 厂商自报偏差

厂商自报可能选择有利的设置、采样温度或版本。项目用“仅第三方”口径整体排除厂商渠道，但第三方榜单也可能有偏差。

### 8.6 人评与 AI 评委的噪声

LMArena、Design Arena、AIWB 等依赖人评或 AI 评委，存在偏好、风格、语言和采样噪声。Elo / Bradley–Terry 分数是相对刻度，不是绝对质量。

### 8.7 内容创作数据偏薄

中文写作的公开可核数据仍然很少。SuperCLUE-Writing 当前只有少量精确同款模型，AIWB 是英文口径。内容创作维请结合自己的素材试稿，不要只看分数。

### 8.8 图片与制图是复合维度

该维同时包含图片理解、细节捕获、前端页面美化与设计复刻。纯文本模型在该维是结构性缺失，不是能力差。

### 8.9 没有置信区间

当前分数是点估计，没有 bootstrap 置信区间，也没有对基准族做统计加权。n=4 是启发式门槛，不是统计显著性检验。

### 8.10 不是采购建议

价格、速度、隐私、部署、供应商稳定性都不在雷达轴内。本项目不构成采购、投资或生产选型建议；高风险场景请自行验证。

## 9. 设计红线

这些规则是项目的“不可妥协项”，改动需要明确的设计讨论：

1. **缺数据 ≠ 0。** 不画到圆心、不按 0 计入综合分、不用推理值静默填充。
2. **速度 / 成本不进雷达轴。** 如需讨论，只能放在图外，且不得变成隐形推荐。
3. **不做未加权平均表盘。** 场景权重必须显式。
4. **负值 / 差值不上雷达。** 雷达只表达 0–100 的能力位次。
5. **一次只用一种口径，并标注数据日期。**
6. **同一基准只算一票。** 由基准族机制强制。
7. **厂商自报只用于该厂商自己的模型，且可整体排除。**
8. **只收精确同款版本。** 不把不同版本、不同设置的分混在一起。
9. **不伪造精度。** 推理值必须标注方法、依据与 LOO 误差，默认不计分。
10. **每条证据可回溯。** 没有 URL 或数据日期的分数不入账。

## 10. 如何复核一个分数

1. 在页面点开该模型 × 维度的证据抽屉；
2. 看“基准族 / 池内 n / 位次分公式”；
3. 找到原始分、来源、日期、URL；
4. 回到来源页面核对原始分与设置；
5. 在 `data/scores.csv` 中搜索该模型与族，确认去重后只剩一票；
6. 如果发现错误，按 [CONTRIBUTING.md](../CONTRIBUTING.md) 提交数据纠错。

最有效的纠错不是“这个分看起来不对”，而是“这条原始证据在这里，版本/设置如下，当前账本漏了/抄错了”。
