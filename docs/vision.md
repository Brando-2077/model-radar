# 项目立意与初心

## 一个普通的问题

这个项目始于一个很普通的问题：

> 当我手上有一个具体任务时，应该选哪个模型？

不是“哪个模型总分最高”，也不是“哪个模型在最新榜单上排第一”，而是：我要写一篇稿、改一个项目、查一份长文档、搭一个多步工作流——哪一个更合适，为什么，证据是什么。

市面上的模型榜单并不少。它们各有各的题目、量表、模型池和更新节奏。问题在于，当我们把这些数字并排放在一起时，很容易产生一种错觉：80 分就是 80 分，第一名就是全面更强。

但 GPQA 的 80 分、Terminal-Bench 的 80 分、写作盲评的 80 分，并不是同一种能力。把它们直接平均，得到的往往不是“综合实力”，而是量表差异、题目难度和模型覆盖率的混合物。

这个项目想做的，是把这团混合物拆开。

## 我们相信什么

### 1. 先分维度，再谈综合

“哪个模型更强”这个问题，只有加上“做什么”才有意义。

写代码需要的是把真实工程任务做完；写文案需要的是文风、结构和网感；做 Agent 需要的是工具调用和多步执行；读长文档需要的是有效上下文，而不是窗口数字。把这些能力压成一个总分，会丢掉最重要的信息。

所以我们保留 8 个维度，并让用户按任务场景选择权重。综合分不是唯一的答案，它只是某个场景下的一种取舍。

### 2. 只在同一基准内比名次

不同基准的分数不可直接比较，这是本项目最重要的技术判断。

我们不把原始分直接平均，而是先把同一基准的多种报法归入“基准族”，在族内问一个更朴素的问题：

> 在这个基准的模型池里，它赢过多少比例的对手？

这就是“族内位次分”。它不完美，但比跨量表平均更接近“相对位置”的真实含义。它也让“某个模型在某个基准上很强，但只在单一来源出现”这件事变得可见，而不是被平均掉。

### 3. 缺数据就留白

这是项目的底线，也是很多榜单最容易含糊的地方。

没有证据的维度，不画到圆心，不按 0 分计入综合分，不用推理值悄悄补上。页面上写“待定”，雷达上留断口，条形图上留斜纹，综合分让权重自动让位。

我宁愿承认“不知道”，也不愿用一个看起来精确的数字制造确定感。

### 4. 证据要能回到源头

每一条分数都应该能回答：

- 它来自哪个榜单或模型卡？
- 数据日期是什么时候？
- 原始分是多少、量纲是什么？
- 它被归到哪个维度、哪个基准族？
- 这个族里有多少个模型？
- 它是实测、厂商自报，还是推理补全？

这些信息不是装饰，而是判断可信度的前提。页面把它们放进证据抽屉，数据表把它们写进每一行。

### 5. 不替用户做决定

模型选择从来不只是能力问题。价格、速度、隐私、部署方式、团队熟悉度、供应商稳定性，都会影响最终决定。

这个项目刻意不把价格和套餐放进雷达轴（它们变动快、地区差异大，也不是“能力”）。它只回答一个它有能力回答的问题：**在公开证据范围内，这个模型的能力画像是什么样？**

剩下的决定，应该由使用者结合自己的约束来做。

## 我们不做什么

- **不做“唯一正确”的总榜。** 场景不同，权重不同，答案本来就可能不同。
- **不把缺失当 0。** 缺数据就是缺数据，不是能力差。
- **不伪造精度。** 推理补全默认不计分；厂商自报单独标记，并可整体排除。
- **不覆盖历史版本。** 新版本单列一册，旧版本保留，便于比较升级是否真的发生。
- **不做高风险场景的最终建议。** 医疗、法律、金融等场景请自行验证。

## 我们希望它成为什么

一个可持续维护的**公开证据地图**：

- 对普通用户，它能在一分钟内回答“这个任务该看哪几个模型、为什么”；
- 对开发者，它是一套可复现的数据管线，而不是一张无法追溯的截图；
- 对贡献者，它是一个可以逐行纠错、逐条补证据的开放账本；
- 对模型厂商和评测机构，它是一个尊重原始来源、也敢于指出覆盖不足的对照工具。

它不需要成为最大的榜单，也不需要追每一个新模型。它只需要在每次更新时，仍然诚实地回答那三个问题：

**证据从哪里来？池子有多大？不知道的地方，有没有老老实实留白？**

## 关于开源

这个项目从一个个人工具开始，最终选择开源，是因为它依赖的几乎所有证据都来自公开社区：开源 benchmark、公开模型卡、公开榜单、匿名的人评投票。

把数据管线、口径和限制一起公开，是对这些工作的回馈，也是让项目继续变好的方式。

如果你发现某个分数不对、某个版本对不上、某个基准被归错了族，欢迎直接开 Issue 或 PR。最有价值的贡献，往往不是“再加一个模型”，而是“这里有一条证据，你之前没看到”。
